ROAM DETAIL PAGE — DATA FIELD REFERENCE
========================================
Companion to schema.sql's `roams` and `roam_details` tables and to
assets/js/roam-details-data.js, which is the current client-side source
for the structure documented here. This is the API/JSON contract for a
future database-backed read/write flow; the existing site still loads JS.

WHERE THIS FITS
---------------
roams/roam-list/roam.html is now the ONE template for every roam's full
detail page (it replaced arabisya-indino.html, coromandel-crest.html and
goanique-ganeshika.html — three near-identical hand-copied files). It's
opened as:

    roams/roam-list/roam.html?slug=<slug>

and assets/js/roam-render.js reads ROAM_DETAILS[<slug>] (currently a
plain JS object loaded from assets/js/roam-details-data.js) and builds
the whole page from it. The `roams` table in schema.sql already covers
the lightweight CARD data (title, route, dates, thumbnail, blurb) shown
on roams.html and in the nav dropdown — this file covers everything
needed for the FULL page, one level deeper.

To go live with a real backend: replace the two <script> tags that load
roams-data.js / roam-details-data.js with a fetch("/api/roams/<slug>")
call that returns the same shape described below, and nothing in
roam-render.js needs to change.

TOP-LEVEL OBJECT
-----------------
Keyed by `slug` (same slug as the `roams` table / card data).

  slug          string   URL identifier, e.g. "goanique-ganeshika".
                         Should equal roams.slug (FK / join key).
  pageTitle     string   Browser tab title, e.g. "Goanique Ganeshika".
                         (Usually just the roam's title; kept separate
                         in case it should ever differ, e.g. for SEO.)

1. HERO (top banner)
---------------------
  hero.image        string   Full-bleed banner photo URL.
  hero.imageAlt      string   Alt text for that photo.
  hero.by            string   Byline, e.g. "By the team of EPSOT Round Trip".
  hero.title         string   Large H1 — the roam's display name.
  hero.subtitle      string   One-line pitch under the title.
  hero.meta          array    List of short "chip" strings shown as
                               pills, e.g. ["<strong>14–22 Oct 2026</strong>",
                               "Mumbai → Gujarat → Jaipur → Delhi", "9 days"].
                               Order matters; may contain inline <strong>.

2. ABOUT (the "why this trip" narrative block)
-----------------------------------------------
  about.heading      string   Section heading, e.g. "Immersion over sightseeing".
  about.paragraphs    array    Ordered list of paragraph strings (may contain
                                inline <a>/<strong>/em>). Rendered in order.
  about.quote         string   Single pull-quote shown in a <blockquote>.
                                Optional — omit/empty to skip rendering it.
  about.objectives    array    Bullet list of trip objectives/goals.
  about.image         string   Supporting photo next to the text.
  about.imageAlt       string   Alt text for that photo.
  about.badge         string   Small overlay label on the photo,
                                e.g. "9 days, 4 states".

3. GALLERY ("where this trip actually takes you")
---------------------------------------------------
  gallery.heading     string   Section heading.
  gallery.subtitle    string   Section subheading/intro line. Optional.
  gallery.cards       array    2–4 photo cards, each:
    .image              string   Card photo URL.
    .imageAlt            string   Alt text.
    .title              string   Card heading, e.g. "The Pink City".
    .text               string   1–2 sentence card description.

4. ITINERARY ("Day by day")
-----------------------------
  itinerary.heading    string   Section heading.
  itinerary.subtitle   string   Section intro line. Optional.
  itinerary.items      array    ORDERED list, mixing two item shapes —
                                 order in the array is the display order,
                                 so a note can sit between any two days:

    { type: "day",
      dayNumber:  string   e.g. "1" (kept as a string: some itineraries
                           use "1–2" for a combined day),
      festive:    boolean  true gives the day a highlighted style
                           (used for the main festival/event day),
      title:      string   Day's heading, e.g. "Arrival in Mumbai + Sanctuary".
      activities: array    Ordered bullet list for that day. }

    { type: "note",
      text: string  A callout between two days, e.g. "Day 7 tends to
                     run long — keep Day 6 short." Rendered as a plain
                     highlighted strip, not inside a day card. }

5. INCLUSIONS / EXCLUSIONS ("What's covered")
-------------------------------------------------
  inclusions.heading        string   Section heading, e.g. "What's covered".
  inclusions.includedTitle  string   Left-column heading, e.g. "What's included".
  inclusions.included       array    Bullet list of what's included.
  inclusions.includedNote   string   Small note under the included list.
                                     Optional.
  inclusions.excludedTitle  string   Right-column heading, e.g. "What's not included".
  inclusions.excluded       array    Bullet list of what's excluded.
  inclusions.excludedNote   string   Small note under the excluded list.
                                     Optional.

6. PACKING ("What to pack")
------------------------------
  packing.heading     string   Section heading.
  packing.subtitle    string   Section intro line. Optional.
  packing.categories  array    Each:
    .title    string   Category name, e.g. "Clothing", "Rain gear".
    .items    array    Bullet list for that category.

7. ELIGIBILITY + PRICE ("Who this trip is for")
---------------------------------------------------
  eligibility.heading     string   Left-column heading, e.g. "Who this trip is for".
  eligibility.criteria    array    Bullet list of who should join.
  eligibility.note        string   Small italic note under the criteria.
                                    Optional.
  eligibility.priceLabel  string   e.g. "Trip cost".
  eligibility.price       string   Display price, e.g. "USD 380–415"
                                    (kept as a display string, not split
                                    into numeric min/max, since ranges and
                                    currency formatting vary per roam).
  eligibility.priceNote   string   Small note under the price,
                                    e.g. what's NOT included in that figure.

8. FAQ ("Questions people ask")
-----------------------------------
  faq.heading   string   Section heading.
  faq.items     array    Each:
    .question    string   Shown as a collapsed <summary>.
    .answer      string   Shown when expanded.

9. FOOTER (closing "Thank You" band, specific to this roam)
----------------------------------------------------------------
  footer.image         string   Full-bleed closing photo.
  footer.imageAlt        string   Alt text.
  footer.thanksText     string   Large heading, normally "Thank You".
  footer.dates          string   Trip dates shown under the heading.
  footer.logo           string   Small roam-specific logo/crest image.
  footer.logoAlt         string   Alt text for the logo.
  footer.presentedBy    string   e.g. "Presented by EPSOT | Embark Pedia".

NOT included here (lives in the `roams` summary table instead, or is
site-wide rather than per-roam): header/nav, the site-wide footer links
(Terms/Privacy/Cancellation/FAQs), and social links.


CURRENT DATABASE MAPPING
========================
`database/schema.sql` creates `roam_details` with one row per `roams.id`
and JSON columns for `hero`, `about`, `gallery`, `itinerary`, `inclusions`,
`packing`, `eligibility`, `faq`, and `footer`. `page_title` is stored in its
own column. An API can join `roams` to `roam_details`, then return the merged
object in the shape consumed by `roam-render.js`.

The organizer requirements also call for named hotels/check-ins. Those are
stored in ordered rows in `roam_stays` (one row per check-in/hotel stop), not
inside the JSON. `roams.days` stores the duration for listings and organizer
validation. The usual 9–11 day ROAM range is a server-side warning/validation
rule, not a database CHECK constraint.

This JSON-backed approach preserves the existing renderer contract and is a
reasonable fit while the admin/editorial application is not yet implemented.
If itinerary days, FAQs, gallery cards, or packing categories later need
independent queries or drag-and-drop editing, normalize them into child tables
with a parent ID and an explicit `position` column. The same current-vs-future
boundary is documented in `database/README.md`.
